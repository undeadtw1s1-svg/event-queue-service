# Event Queue Service

Небольшой сервис на Flask и SQLite для приёма вебхуков и асинхронной обработки событий через собственную очередь задач.

## Как запустить

1. Установить зависимости:
```bash
pip install -r requirements.txt
```

2. Запустить приложение:
```bash
python app.py
```

Сервис поднимется на `http://127.0.0.1:5000`. При старте автоматически создаётся база данных `app.db` и запускается фоновый поток воркера.

## Примеры запросов

Отправка вебхука:
```bash
curl -X POST http://127.0.0.1:5000/webhook \
  -H "Content-Type: application/json" \
  -d '{"event_id": "pay-101", "type": "payment_succeeded", "payload": {"amount": 1000}}'
```

При первом запросе возвращается `200 OK` и задача встаёт в очередь.
При повторной отправке с тем же `event_id` сервис возвращает `200 OK`, но дубликат не создаётся и повторно в очередь не уходит.

Просмотр статистики:
```bash
curl http://127.0.0.1:5000/stats
```

Ответ:
```json
{
  "events_by_type": {
    "payment_succeeded": 1
  },
  "tasks_by_status": {
    "failed": 0,
    "pending": 0,
    "skipped": 0,
    "success": 1
  }
}
```

## Тесты

Запуск тестов:
```bash
pytest test_app.py -v
```

Тесты проверяют:
- идемпотентность `POST /webhook` (повторный `event_id` не создаёт дублей и отдаёт 200);
- валидацию входных данных (пустые поля, некорректный JSON, статус 400);
- логику 3 попыток с нарастающей паузой (backoff 1s, 2s, 4s) и переход в `failed`;
- корректный подсчёт статистики на `/stats`;
- защиту от зависания задачи в `pending` при любом падении обработчика.

## Принятые решения

1. **Идемпотентность**:
   На поле `event_id` в таблице `events` повешен `UNIQUE`. Вставка события и создание связанной задачи в `tasks` происходят в одной транзакции. Если запись уже существует, транзакция откатывается и эндпоинт отдаёт 200 без создания второй записи.

2. **Очередь задач и воркер**:
   По условию нельзя было использовать Celery/RQ, поэтому очередь сделана на отдельной таблице `tasks`.
   Воркер запущен в фоновом потоке (`threading.Thread`). Он выбирает задачи со статусом `pending`, у которых подошло время `next_retry_at`.
   Для потокобезопасности SQLite операции с базой изолированы через `threading.RLock`.

3. **Ретраи и паузы**:
   Если обработка падает с ошибкой, счётчик `attempts` увеличивается на 1.
   Задержка рассчитывается по формуле `2 ** (attempts - 1)`:
   - 1-я ошибка: повтор через 1 сек
   - 2-я ошибка: повтор через 2 сек
   - 3-я ошибка: повтор через 4 сек
   После 3-й неудачной попытки статус задачи переключается в `failed`, и больше воркер её не трогает.

4. **Защита от зависания в pending**:
   Вся обработка задачи завёрнута в блок `try ... except BaseException`. Даже если хендлер словит непредвиденную ошибку или исключение, задача всегда обновит свой счётчик попыток и получит статус `failed` или обновлённый `next_retry_at`, так что задача не останется в `pending` навсегда.

5. **Почему SQLite**:
   Сервис лёгкий, под условия тестового SQLite подходит идеально. Чтобы не ловить ошибки конкурентного доступа между Flask-обработчиком и воркером, используется `check_same_thread=False` с таймаутом и потоковый замок `RLock`.
